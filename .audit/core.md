# Core audit — bugs introduced between 1.7.2 and HEAD

Scope: `KeyViewer.cs`, `KeyViewerInput.cs`, `KeyViewerLayout.cs`, `KeySource.cs`.

## Per-key count text is forced to pure white when only the label text gradient is on
- file: JipperKeyViewer/KeyViewer/Core/KeyViewerInput.cs
- line: 643-679
- severity: medium
- what: `UpdateKeyColors` forces `key.text.color = Color.white` whenever `EnableKeyTextGradient` is on (the white base the glyph-gradient pass multiplies against). The very next block then does `if (!d.EnableCountTextGradient) key.value.color = key.text.color;` — so when the *label* gradient is on but the *count* gradient is off, the count's own configured colour is overwritten with that forced white instead of the solid colour it should keep. The full-keyboard branch (line 646) has the identical mistake.
- path: Fixed layout + `EnableKeyTextGradient = true` + `EnableCountTextGradient = false` → press any key → `ProcessKeyGroup` (KeyViewerInput.cs:363) → `UpdateKeyColors(idx, current, d)` → `key.text.color` becomes white (643/659/667) → line 677 copies white onto `key.value`. `TickTextGradients` → `ApplyTextGradient(key.value, countOn:false, …)` (KvTextGradient.cs:145-148) only restores a solid colour if `textGradientStates` already holds an entry for that text, i.e. only if the count gradient had been on before. With it off from the start there is no entry, so nothing ever puts the colour back, and every subsequent press re-applies white. Visible result: all per-key count numbers render pure white (invisible on light key backgrounds) instead of `Text`/`PerKeyText`. At 1.7.2 the line was `key.value.color = key.text.color` with `text.color` still the real colour, so this is a regression.
- fix: compute the count's solid colour independently of the label's forced white, e.g. `key.value.color = d.EnableCountTextGradient ? Color.white : ResolveSolidTextColor(key, /*count*/ true);` (that resolver already handles per-key / full-keyboard / KPS / Total / pressed), and do the same in the `IsFullKeyboard` branch.

## Fixed-layout key glows keep their pre-position rect after custom positioning is applied
- file: JipperKeyViewer/KeyViewer/Core/KeyViewerLayout.cs
- line: 135-137 (and 1789-1797, 1879-1881)
- severity: medium
- what: `ApplyFixedGlow` derives the halo rect from `key.transform`'s `anchoredPosition` (CustomLayout.cs:1091-1092), but `SetKeyPosition` — the only thing that applies the custom-position offset — updates the key root, the text wrapper and the merged shape slot, and never the glow Image. `BuildOverlay` and `ResetKeyViewer` therefore call `ApplyFixedKeyGlows()` *before* `ResetKeyViewerPosition()`, and the glows are left at the unshifted coordinates.
- path: `EnableFixedKeyGlow = true` + `CustomPositionEnabled = true` with a non-zero `MainKeyViewerPosition`/`FootKeyViewerPosition` → `Update` (KeyViewer.cs:651-656) or `OnEnable` (KeyViewerLayout.cs:516-520) calls `EnableKeyViewer()` → `BuildOverlay()` line 135 `ApplyFixedKeyGlows()` captures the layout coordinates → the caller then runs `ResetKeyViewerPosition()` → `SetKeyPosition` moves the keys and their shape rects only. Every key box and text is offset by the custom position while its halo stays put, so a visible glow ghost trails the key. The only thing that repairs it is the next press (`UpdateKeyColors` → `ApplyFixedGlow`), so a key that is never pressed keeps a frozen halo forever. Same ordering bug on the foot-key-only path (`ResetFootKeyViewer` lines 1879-1881) and on `ResetKeyViewer` (1789 then 1796-1797).
- fix: call `ResetKeyViewerPosition()` before `ApplyFixedKeyGlows()` in `BuildOverlay`/`ResetKeyViewer`/`ResetFootKeyViewer`, and/or have `SetKeyPosition` reposition the cached glow (`SetFixedGlowRect(key)`) the same way it updates `keyShapeLayer.SetRect`.

## `SaveCurrentProfile`'s forward DataVersion stamp defeats `MigrateFootSlots`' unknown-foot-style escape hatch
- file: JipperKeyViewer/KeyViewer/Core/KeyViewer.cs
- line: 1324-1330 vs 1885-1886
- severity: low
- what: `MigrateFootSlots` deliberately returns *without* raising `DataVersion` when the profile carries a `FootKeyviewerStyle` this build does not recognise, with the stated contract "leave the profile at its old version so a build that does know the style still shifts it". `SaveCurrentProfile` then unconditionally does `if (Settings.Data.DataVersion < Settings.Version) Settings.Data.DataVersion = Settings.Version;`, which raises it to 6 on the very next save and closes the gate permanently.
- path: A v3-era profile whose `FootKeyViewerStyle` is an integer this build does not define (written by a newer build, or hand-edited) → `LoadProfile` → `MigrateFootSlots(pd)` logs the warning and returns with `DataVersion` still 3 → `LoadProfileFromMeta`/`SwitchProfile` call `EnsureSettingsArrays()`, which clamps the style to `None` (KeyViewer.cs:1537-1541) → the next `SaveSettings` (every scene load, `OnSceneLoaded`) stamps `DataVersion = 6` → the v3-era foot counters that were sitting on slots 20.. are never shifted to 24.. and read back as a permanent 0. That is exactly the round-38 bug the refactor set out to close, and the gate can never re-open once written.
- fix: in `MigrateFootSlots`, mark the profile so the forward stamp cannot consume the gate (e.g. set a dedicated `FootSlotsDeferred` bit/flag and have `SaveCurrentProfile` skip the `DataVersion` bump for it), or clamp the enum in `LoadProfile` *before* calling `MigrateFootSlots` and treat a clamped style as "no shift needed but do not stamp".

## `WriteAllTextSafe`'s `File.Replace` fallback can delete both the live file and the new content
- file: JipperKeyViewer/KeyViewer/Core/KeyViewer.cs
- line: 1843-1871
- severity: low
- what: The new `PlatformNotSupportedException` fallback does a non-atomic `File.Delete(path)` followed by `File.Move(tmp, path)`. If the move fails (an AV/indexer handle, a permissions change, a mid-operation failure on the exFAT/network share where this fallback is the *only* path that ever runs), the outer `catch` deletes `tmp` as well and rethrows — so neither the old file nor the new content survives.
- path: Any `SaveCurrentProfile` / `SaveMetaOnly` on a Mono/Wine/Proton or network/exFAT config directory where `File.Replace` is unimplemented → `File.Replace` throws → `File.Delete(path)` removes the only good copy of `settings.json` or `<profile>.json` → `File.Move` throws → `catch` at 1864 runs `File.Delete(tmp)` and rethrows → the caller (`SaveSettings`/`GuardedSave`) only records `lastSaveError`; the user's config is gone and there is no `.corrupt` backup, because `RotateCorruptBackup` only runs on a *load* failure. Narrow window, but it is unrecoverable user-data loss on exactly the platforms the fallback exists for.
- fix: move the temp file into place first and only remove the original if the move succeeded (e.g. `File.Copy(tmp, path, true)` then `File.Delete(tmp)`, or move the original aside to `<path>.bak` and only unlink it after the new file is in place), and never delete `tmp` when the live file is already gone.

## A single missing profile file pins the meta at v5, so the v5→v6 migration re-runs on every launch forever
- file: JipperKeyViewer/KeyViewer/Core/KeyViewer.cs
- line: 1253-1258 and 1286-1292
- severity: low
- what: `MigrateV5toV6` now treats "file listed in `ProfileNames` but not readable *right now*" as a migration failure and rolls the meta back to 5 so the pass retries. A name that simply has no file on disk is a permanent, not transient, condition, and nothing ever removes it from `ProfileNames` before the gate is evaluated — so `Settings.Version` can never reach 6 and the whole batch pass (plus a warning line) re-executes on every single launch.
- path: `ProfileNames` contains a name whose `.json` is absent (deleted while the game was closed, a OneDrive placeholder, an orphan cleaned by hand) while the meta is at version 5 → `LoadSettings` → `MigrateV5toV6(5)` → the loop hits `!File.Exists(path)` and sets `allProfilesSucceeded = false` → `Settings.Version = 5; return;` skips `SaveMetaOnly()`. `SyncProfilesWithDisk` later drops the stale name, but it then writes the meta with `Settings.Version == 5`, so the gate stays at 5. Next launch: `MigrateV5toV6` runs again, re-reads and re-serialises every other profile file to re-check it, and logs the same warning. The current profile's flip is not repeated (it is gated on `DataVersion >= 6`), so nothing is corrupted — but the migration can never complete and the per-launch cost/warning noise is permanent.
- fix: distinguish "missing" from "temporarily unreadable" (only count an existing-but-unreadable file as a failure), or drop names with no file from `ProfileNames` before evaluating the gate, so a permanent condition does not hold the meta at v5 indefinitely.
